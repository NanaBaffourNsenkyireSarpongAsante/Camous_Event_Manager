What Was Already in Place (Before These Changes)

The following features were fully working before any of the changes documented here were applied:

  • Authentication system: user registration, login, email verification flow, and JWT-based session management.
  • Frontend views: Home, Events listing, Organizer Dashboard, Event Details, Tickets, Calendar, FAQ, and Profile pages — all built with Vanilla JS.
  • Auth frontend wired to the backend: the signup, login, and email-verification forms communicated with /api/auth/register, /api/auth/login, and /api/auth/verify/:token correctly.
  • Event CRUD on the frontend: organizers could create and edit events, but all data was stored only in localStorage. Nothing was persisted to a database.
  • Broken deleteEvent(): the function existed but was completely non-functional. It used .error() (which is not a method on a Promise), referenced res (a server-side Express object that does not exist in the browser), and even when the fetch succeeded, the result was discarded and local state was never updated.

models/event.js — Mongoose Event Schema

NEW FILE

This file defines the data shape for every event stored in MongoDB. Without this schema, there was no way for the backend to read or write events to the database.

Schema Fields

Field Type Rules Notes
titleStringRequiredEvent name
dateStringRequiredDate string (e.g., "2026-04-15")
timeStringRequiredTime string (e.g., "14:00")
venueStringRequiredLocation of the event
categoryString (enum)RequiredAcademic / Social / Tech / Arts / Music / Sports / Other
ticketNumberDefault: 0Price in Ghana Cedis; 0 means Free
descriptionStringRequiredFull event description
imageStringOptionalURL to a cover image; nullable
organizerObjectId (ref: User)Optional at schema levelSet at creation time from JWT; enables ownership checks
createdAtDateAuto (timestamps)Automatically managed by Mongoose

Virtual ID Field

The schema includes eventSchema.set('toJSON', { virtuals: true }). This instructs Mongoose to include an id string field (a plain-string alias for _id) in every JSON response. This is important because the frontend uses event.id — if this line were omitted, the frontend would receive only event._id (an ObjectId object), and all event lookups by ID on the client would silently fail.

controllers/eventController.js — Event API Handlers

NEW FILE

This file contains the four request handler functions that implement the events API. Each handler is an async function wrapped in a try/catch block so unexpected errors are logged and return a proper 500 response instead of crashing the server.

getEvents — GET /api/events (Public)

Queries the Event collection for all documents, sorted by createdAt descending (newest first), and returns them as a JSON array. No authentication is required — anyone can browse published events.

createEvent — POST /api/events (Auth Required)

Validates that all required fields are present in the request body. If any are missing, it returns HTTP 400 with a descriptive error. On success, it sets organizer to req.userId (populated by the JWT middleware), saves the document, and returns the newly created event object with its real MongoDB _id.

updateEvent — PUT /api/events/:id (Auth Required)

Uses findOneAndUpdate with a filter of both { _id: req.params.id, organizer: req.userId }. This dual-condition filter is the ownership check: an organizer can only edit an event they created. If the event does not exist, or belongs to a different user, the query returns null and the handler responds with HTTP 404.

deleteEvent — DELETE /api/events/:id (Auth Required)

Uses findOneAndDelete with the same dual-condition filter as updateEvent. Responds with { success: true, message: 'Event deleted successfully' } on success, or HTTP 404 if the event is not found or not owned by the requesting user.

Security note: Because every mutating operation (create, update, delete) passes through the authMiddleware before reaching these handlers, unauthenticated requests are rejected before a single database query is made.

controllers/authController.js — updateProfile Added

UPDATED

A new handler function updateProfile was added to the existing auth controller. This handler allows a logged-in user to update their display name, phone number, and avatar URL.

What Can Be Updated

  • name — validated to be non-empty before saving
  • phone — optional contact number
  • avatar — URL to a profile image

What Cannot Be Updated

email and studentId are identity fields — they are used for login and verification and must remain immutable once set. Even if a client sends these fields in the request body, the handler ignores them.

Implementation Detail

The handler uses findByIdAndUpdate(req.userId, { name, phone, avatar }, { new: true }). The req.userId value comes from the JWT middleware, so there is no way for a user to accidentally update someone else's profile by guessing an ID. The returned user object has the password field removed before it is sent back to the client.

server.js — Events Router Mounted

UPDATED

A single line was added to register the new events router with the Express application:

app.use('/api/events', require('./routes/events'));

Without this line, all requests to /api/events/* would return a 404, even with the router and controller files in place. This line is what connects the URL namespace to the route handler logic.

KEM frontend/main.js — Multiple Frontend Fixes

UPDATED

This was the most extensive set of changes. Seven individual fixes were applied to wire the frontend to the real backend APIs and correct broken logic.

Fix A — Token Storage After Login

Problem: The backend's login endpoint returned a JWT token in data.token, but handleLogin() never stored it anywhere. Every subsequent API call that required authentication had no token to send, so they all failed silently.

Fix: Added localStorage.setItem('kem_token', data.token) immediately after a successful login response. This token is now available for all subsequent authenticated API requests.

Fix B — Token Cleared on Logout

Problem: The logout() function cleared currentUser from localStorage but left the JWT token in place. A user who logged out still had a valid token stored, which is a security concern.

Fix: Added localStorage.removeItem('kem_token') to logout().

Fix C — loadEventsFromAPI() Function (New)

Problem: There was no mechanism to populate the frontend's events array from the database. Every page load started with whatever happened to be in localStorage.

Fix: Added a new async function loadEventsFromAPI() that:

  • Sends GET /api/events (no auth needed)
  • Stores the response in the module-level events array
  • Caches the result in localStorage as a fallback for offline use

This function is called in two places: immediately after a successful login (before showing the main app), and on page load when an existing session is restored from localStorage.

Fix D — saveEvent() Wired to API

Problem: Creating or editing an event used Date.now() as a fake numeric ID and saved only to localStorage. No data ever reached the database, and IDs were not compatible with MongoDB's ObjectId format used in the API routes.

Fix: saveEvent() now reads the #editId hidden form field to distinguish between create and update operations:

  • If editId is empty → sends POST /api/events with an Authorization header
  • If editId has a value → sends PUT /api/events/:id with an Authorization header

On a successful response, the local events array is updated with the server's returned event object (which carries the real MongoDB id). The UI is then refreshed by calling renderDashboard(), renderEventsGrid(), and renderTrainEvents().

Fix E — deleteEvent() Completely Rewritten

This was the most broken function in the codebase. Here is the original code followed by the corrected version:

BEFORE (Broken) 
const remove = fetch(`/events/${id}`, { method: 'DELETE', ... })
  .then(response => {response.json()})   // missing return — result discarded
  .error(() => {res.status(500)...})     // .error() does not exist on Promise
                                         // res is a server-side Express object —
                                         // it does not exist in the browser
AFTER (Correct) 
const response = await fetch(`/api/events/${id}`, {
  method: 'DELETE',
  headers: { 'Authorization': `Bearer ${token}` }
});
const data = await response.json();
if (data.success) {
  events = events.filter(e => e.id !== id);
  saveEvents(events);
  renderDashboard();
  renderEventsGrid();
  renderTrainEvents();
}
// Error handling uses .catch() — the correct Promise API

The three specific bugs that were fixed:

  1. .error() does not exist — Promises use .catch() for error handling.
  2. res is undefined in the browser — res is Express's response object, which only exists on the server. Referencing it in frontend JavaScript causes a ReferenceError.
  3. Local state was never updated — even if the server deleted the record, the frontend events array still contained the deleted event, so it continued to appear in the UI.

Fix F — saveProfile() Wired to API

Problem: Profile updates changed only the in-memory currentUser object and saved it to localStorage, but never reached the backend. Refreshing the page would revert changes, and the database was never updated.

Fix: saveProfile() now sends PUT /api/auth/profile with name, phone, and avatar in the request body (with an Authorization header). On a successful response, the returned data.user object is merged into currentUser and saved to localStorage.

Note: The email and studentId fields are rendered as read-only in the profile form and are intentionally not included in the request body — they are identity fields that should never be changed after registration.

Fix G — saveEvents() Parameter Rename

Problem: The saveEvents(events) function had a parameter also named events, which shadowed the module-level events variable inside the function body. This is a subtle scoping bug — any code inside the function that intended to reference the module-level array would silently read the parameter instead.

Fix: The parameter was renamed from events to evts, eliminating the variable shadowing.

KEM frontend/index.html — "Back to Sign Up" Button

UPDATED

A "Back to Sign Up" button was added to the Role Selection screen.

Why This Was Needed

The sign-up flow worked as follows: a user clicks "Sign Up", fills in the registration form, and submits. The frontend then hides the auth form and displays the Role Selection screen (where the user picks Student or Organizer). There was no way to go back.

This was the root cause of user-reported confusion around "why can't I switch between sign up and sign in" — once the role selection screen appeared, the only option was to reload the page. The auth container was completely inaccessible.

The Fix

The new button calls showAuth(); switchAuthTab('signup'); which performs two actions:

  1. Shows the auth container (hides the role selection screen)
  2. Re-activates the Sign Up tab, so the user lands back exactly where they left off

Architecture Summary (After All Changes)

Browser (main.js) ↕ JWT in Authorization header Express Server (server.js) /api/auth → routes/auth.js → controllers/authController.js /api/events → routes/events.js → controllers/eventController.js / → serves KEM frontend/ (static files) ↕ MongoDB (Mongoose) User model (models/user.js) Event model (models/event.js) ← NEW

Data Flow for Event Creation

  1. Organizer fills out the "Create Event" form in the browser.
  2. saveEvent() sends POST /api/events with the JWT in the Authorization header.
  3. authMiddleware verifies the token and attaches req.userId.
  4. createEvent controller validates fields, sets organizer: req.userId, and saves to MongoDB.
  5. The server returns the saved event (with its real MongoDB id).
  6. The frontend updates its local events array and re-renders all event lists.
